Hybrid 模型的 prefix cache

两种记忆，
一张缓存

Qwen3-Next、Qwen3.5、Kimi Linear 这类 hybrid 模型同时有 attention 层和 recurrent 层（GDN、Mamba）。两种层记东西的方式完全不同，prefix cache 必须同时照顾两边。下面每一节都有一个可以动手的小实验，讲 vLLM、SGLang 和 Marconi 各自怎么做。

01

两种记忆

attention 可以截断，state 只能精确命中

attention 层给每个 token 留一块 KV。想从第 p 个 token 接着算，把 KV 截到 p 就行。

recurrent 层只有一个固定大小的 state，每读一个 token 就原地覆盖一次。它回不到过去：想从 p 接着算，必须事先在 p 处存过一份 state 的拷贝，也就是 checkpoint。

拷贝很贵。以一个 GDN 模型的配置为例，一个 GDN state 是 3.12 MiB，相当于 799 个 token 的 KV。

所以 hybrid 模型的命中长度，等于 attention 和 recurrent 两边都能恢复的公共位置。剩下的问题只有三个。

Admission · 在哪存

每 N 个 token 存一个，只在 chunk 边界存，还是只在分支点存？

存太密会占满显存。vLLM 观察到密集快照占掉 80% 的 pool。

Matching · 怎么对齐

attention 匹配到 2432，最近的 checkpoint 在 1792。

只能从 1792 恢复，多匹配的 640 个 token 要重算。

Eviction · 淘汰谁

KV 的大小正比于它省下的算力，state 不是。

代表 token 越多的 state 越值钱，LRU 会误删它们。

02

内存布局

一个大池子，还是两个池子

vLLM 让所有层共用一个 block pool。为了让同一个 block 既能装 attention KV，也能装一个 state，它把 attention 的 block 撑大：3.12 MiB ÷ 4 KiB ≈ 799，向上对齐到 128 的倍数就是 896。启动日志里的 Setting attention block size to 896 tokens 就是这么来的。

SGLang 分两个池：state 按请求分 slot，KV 按 token 分 page。attention 的粒度不受影响；代价是 state 池按比例静态切出去，每个 running request 还要预留 3 到 5 个 slot。

03

vLLM · 匹配、写入、896

匹配取交集，写入看网格

匹配时，每种层一个 manager，各找各的命中长度，然后取所有层都能恢复的最长位置。候选长度只缩不涨，直到不再变化。

三个 manager 怎么找示意图

写入更受限。GDN 类模型只能用 align 模式：只有当一个 prefill chunk 恰好结束在 896 的倍数上，那里的 state 才会被冻结成能命中的 checkpoint。所以 scheduler 会主动把 chunk 切在 block 边界上。

问题出在它用哪个网格切。scheduler 读的是 cache_config.block_size，也就是所有 cache group 里最小的 block size。只要有一个更小 block 的 group，切分网格就和 GDN 网格对不上。例如 128 对 896 的配置就是这样。

试试这几个预设

  • 不加 flag：chunk 结束在 2048、2304、2528，没有一个是 896 的倍数，slot 全空，三个请求都命中 0。
  • 只加 --block-size 896：896 能存下来，但读侧上限只有 896，命中卡在 896。
  • 两个都加：REQ2 在共享前缀交点 1792 断开，写下 1792；REQ3 才命中 1792。cache 是一步步暖起来的。
  • PR #54076：每跨过一个 block 边界都断开，REQ1 自己就写下 896 和 1792，REQ2 直接命中 1792。
  • 长 prompt 的错位：n = 4000 时，slot 2 冻结着 2048 处的 state，却被当成 2688 发布出去。REQ2 命中它，用的是过时的 state，输出会悄悄变错。

PR #54076 改了三处

① 切分网格

用 Mamba group 自己的 block size，不再用所有 group 的最小值。

今天 main 的 scheduler.py:443 仍是 cache_config.block_size。

② 边界强制断开

每跨过一个 block 边界都结束 chunk，从对齐位置开始也一样。

原来一个 chunk 能跨 k 个 block，中间 k − 1 个 slot 一直为空。

③ 回退范围

最后一个 block 的回退只对 eagle、eagle3、mtp 生效。

DFlash 和 DSpark 用自己的 KV，不再回退。对 MTP 没有影响。

04

Marconi 与 SGLang · radix tree

树上的 state 挂在哪里

SGLang 和 Marconi 都用 radix tree。边上存 KV，节点上可以挂一份 state。匹配时沿树往下走，只能停在挂着 state 的位置；attention 多匹配的部分要重算。

三种 admission 策略的区别，在于什么时候往树上挂 state：

  • Marconi：只在分支点和请求结束时存。分支点要等第二个请求来才发现，第三个起才命中。
  • SGLang no_buffer：每个 chunk 边界、prompt 末尾、请求结束都存，位置精确，但要关掉 overlap。
  • SGLang extra_buffer：chunk 边界按 64 对齐，再加上分支点；decode 每 256 个 token 存一次，所以请求结束时只缓存到最后一次存的位置。

淘汰：LRU 只看最近用没用过。Marconi 的 FLOP-aware 还看这个 state 代表多少 token，越长越值钱。

同一串请求，三种策略的总账

教学模型：token 长度为示意，chunked prefill 每块 1024 token，只限制 state 数量，KV 视为足够。试试：选 Marconi，把上限调到 5，再在 LRU 和 FLOP-aware 之间切换。LRU 会丢掉文档 A 分支点上的 state，R5 只能从 1,024 恢复；FLOP-aware 保住它，R5 从 2,560 恢复。

SGLang 实现上的几个细节

  • 延迟 CoW：命中时只记下源 slot，forward 时在 mamba 层之前把 state 拷到请求自己的 slot。树里的 checkpoint 永远不被原地修改。
  • tombstone：内部节点可以只丢 state、保留 KV。节点分裂时，新父节点也是 tombstone，因为 state 不能切分。
  • 现状：UnifiedRadixCache 对所有模型默认，树核心默认用 Rust；旧的 MambaRadixCache 已删除（#40313）。淘汰策略可选 lru、lfu、slru、priority、tlru，仍没有 FLOP-aware。
  • 投机解码：verify 不推进持久 state，每个 draft token 的 state 先写进 intermediate_ssm，verify 后把被接受的那一步拷回。
05

放在一起看

同一个抽象，三种取舍

三者都收敛到同一件事：attention 决定上界，recurrent state 决定能不能落地。差别在 checkpoint 的密度、位置策略，以及显存怎么分。

维度vLLMSGLangMarconi

GDN 加 MTP 的 prefix caching，目前 SGLang 更稳。vLLM 更通用，但 align 模式对 block 几何很敏感。

SGLang 更好的地方

  • attention 粒度不受影响，短前缀也能命中
  • checkpoint 位置不依赖 block 网格
  • 内部节点可以只丢 state、保留 KV

vLLM 更好的地方

  • 一个 pool 自动分配，并发上限更高
  • full、SWA、Mamba 统一框架，connector 生态全
  • 稀疏保留、交点 checkpoint、partial hit 都有

这是读代码和公开数据得出的判断，没有在同一个 workload 上做过对比实测。
